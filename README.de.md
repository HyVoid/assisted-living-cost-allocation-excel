## Finanzcontrolling in der Seniorenpflege: Schmerzpunkte & Lösungen zur Kostenumlage

Ein Betrieb für Betreutes Wohnen oder Seniorenpflege mit mehreren Standorten verwaltet oft mehrere Gebäude, die unabhängig Umsatz erwirtschaften, gleichzeitig aber stark auf gemeinsame Unternehmens-Overheads, regionale Pflegedienstleitungen, Fahrzeugflotten und zentrale Verwaltung angewiesen sind. Die entscheidende Finanzfrage ist nicht nur die Verfolgung der gesamten Unternehmensausgaben, sondern die Bestimmung, **wo dieser Overhead korrekt anfällt, um die tatsächliche EBITDA der Einrichtung zu berechnen**.

Diese Vorlage ordnet gängige finanzielle Engpässe automatisierten Lösungen zu:

| Schmerzpunkt | Lösung |
| :--- | :--- |
| **Verschleierte Einrichtungsmargen** | Berechnet präzise **Umsatz auf Einrichtungsebene, direkte Betriebskosten, Gemeinkostenbelastung und Nettogewinn** — so wird jedes Pflegeheim und jede Wohneinheit auf einer standardisierten GuV-Grundlage bewertet. |
| **Vermischte Unternehmens- und lokale Ausgaben** | Trennt **direkte Deckungsbeitragsmarge vs. vollständig belastete Rentabilität** — die tatsächliche lokale Wirtschaftlichkeit einer Einrichtung wird vom finanziellen Gewicht der Unternehmensressourcenverteilung isoliert. |
| **Nicht nachvollziehbare Overhead-Verteilungen** | Macht **genau nachvollziehbar, wie gemeinsame Ausgaben über das Portfolio verteilt werden** — der exakte Umlagesatz wird angezeigt und bis zur ursprünglichen Hauptbuch-Transaktion (GL) zurückverfolgt. |
| **Verwaiste oder übermäßig umgelegte Kosten** | Prüft **Umlageregeln auf Unter- oder Überumlage** — eine strenge 100-%-Kontrollprüfung wird durchgesetzt, statt eine unvollständige Aufteilung stillschweigend durchgehen zu lassen. |
| **Gestörte Monatsabschluss-Konsolidierungen** | Automatisiert **die Abstimmung der Ausgaben auf Unternehmensebene** — Quell-AP-Transaktionen, Ausgaben der Umlage-Engine und die finale finanzielle Aufstellung auf Einrichtungsebene werden nahtlos verglichen. |

| Arbeitsblatt            | Rolle                        | Primäre Verantwortung                                       |
| ---------------------- | --------------------------- | ------------------------------------------------------------ |
| `00_Setup`             | Konfiguration & Stammdaten | Parameter, Einrichtungen, Konten, Umlageregeln                |

| `05_Dashboard`         | Managementansicht             | KPIs, Einrichtungsrangfolge, Gemeinkostenbelastung, Trends               |

Die Architektur trennt bewusst **Quelldaten von Umlagelogik**.

Eine Transaktion wird nicht zu einer anderen Transaktion, nur weil sie auf mehrere Einrichtungen umgelegt wird. Die ursprüngliche Transaktion bleibt der Quelldatensatz. Die Umlage-Engine erzeugt daraus abgeleitete analytische Zeilen.

Dies schafft einen Prüfpfad:

```text
Source Transaction
      ↓
Allocation Rule
      ↓
Target Unit + Applied Rate
      ↓
Allocated Amount
      ↓
Unit P&L
      ↓
Consolidated P&L
      ↓
Reconciliation
```

### Drei Fallen, in die selbst erfahrene Betriebsbuchhalter tappen

#### Falle 1 — Gemeinkosten als separate Einrichtungstransaktionen erfassen

**1. Getroffene Entscheidung**

Das Management möchte die Fahrzeugausgabe von 3.000 $ auf drei Einrichtungen verteilen.

**2. Fehlerhafte Zahl**

Anstatt eine einzige Quelltransaktion von 3.000 $ zu behalten, erfasst der Betreiber drei separate Ausgaben.

**3. Geänderte Empfehlung**

Die Berichte auf Einrichtungsebene mögen korrekt erscheinen, aber das Quellhauptbuch hat keine saubere 1:1-Beziehung mehr zum Managementbericht.

**4. Warum die Schlussfolgerung falsch ist**

Die Umlage erfolgt während der Datenerfassung und nicht als kontrollierter analytischer Schritt. Das erschwert es, das ursprüngliche wirtschaftliche Ereignis von der Reporting-Behandlung zu unterscheiden.

**5. Korrigierter Ansatz**

Erfassen:

```text
Vehicle Expense
Source Amount = $3,000
Rule = VEH-001
```

Dann anwenden:

```text
Unit A = 40% → $1,200
Unit B = 35% → $1,050
Unit C = 25% → $750
```

**6. Korrigiertes Ergebnis**

Die drei Einrichtungsberichte erhalten die korrekten Beträge, während die ursprüngliche Transaktion von 3.000 $ intakt und nachvollziehbar bleibt.

**7. Formel**

<details>
<summary>Umlagebetrag</summary>

```excel
=ROUND(Tx_Amount * Applied_Rate, 2)
```

Der Quellbetrag wird erst mit dem Regelprozentsatz multipliziert, nachdem die Transaktion die Eingabevalidierungsschicht passiert hat.

</details>

---

#### Falle 2 — Eine 95-%-Umlage als „gut genug“ behandeln

**1. Getroffene Entscheidung**

Eine Unternehmens-Overhead-Regel verteilt Kosten auf vier Einrichtungen.

**2. Fehlerhafte Annahme**

Die eingegebenen Prozentwerte summieren sich auf 95 %.

**3. Geänderte Empfehlung**

Die resultierende Einrichtungs-GuV unterschlägt den Betrag, der von den Betriebseinrichtungen aufgefangen wird. Die fehlenden 5 % verschwinden faktisch aus der Umlageansicht.

**4. Warum die Schlussfolgerung falsch ist**

Eine gemeinsame Ausgabe ist nach wie vor ein vollständiges wirtschaftliches Ereignis. Eine Regel, die nur 95 % verteilt, hat dieses Ereignis nicht vollständig abgebildet.

**5. Korrigierter Ansatz**

Die Regel muss explizit auf 100 % abstimmen, vorbehaltlich ausschließlich der konfigurierten numerischen Toleranz.

**6. Korrigiertes Ergebnis**

Eine Regel wie:

```text
Unit A   25%
Unit B   25%
Unit C   25%
Unit D   25%
Total   100%
```

wird akzeptiert. Eine 95-%- oder 105-%-Regel wird markiert, bevor sie die normale nachgelagerte Umlage treiben kann.

**7. Formel**

<details>
<summary>100-%-Umlagevalidierung</summary>

```excel
=LET(
    total_pct, [@[Rule_Total_Check]],
    tolerance, cfg_Tolerance,
    diff, total_pct - 1,
    IF(
        ABS(diff) <= tolerance,
        "✅ OK",
        IF(
            diff < 0,
            "⚠️ Under 100%",
            "❌ Over 100%"
        )
    )
)
```

Die Toleranz wird zentral gesteuert statt fest in die Regel codiert.

</details>

---

#### Falle 3 — Einrichtungsrentabilität vertrauen, ohne den Unternehmensgesamtbetrag abzustimmen

**1. Getroffene Entscheidung**

Ein regionaler Manager prüft die Einrichtungs-GuV und sieht, dass jede Einrichtung einen plausiblen Ausgabenbetrag ausweist.

**2. Fehlerhafte Zahl**

Die einzelnen Berichte wirken plausibel, aber der kombinierte umgelegte Betrag stimmt nicht exakt mit der Quellausgabenpopulation überein.

**3. Geänderte Empfehlung**

Das Management könnte schlussfolgern, dass die Einrichtungen gemeinsam eine bestimmte Marge erwirtschaftet haben, während der zugrunde liegende Umlageprozess tatsächlich Kosten ausgelassen oder verdoppelt hat.

**4. Warum die Schlussfolgerung falsch ist**

Plausible einzelne Zahlen belegen nicht, dass das Reporting-System vollständig ist.

**5. Korrigierter Ansatz**

Der Unternehmensgesamtbetrag muss über drei verknüpfte Populationen geprüft werden:

```text
Source Transactions
        ≡
Allocation Engine
        ≡
Unit P&L Roll-up
```

**6. Korrigiertes Ergebnis**

Eine Abstimmungsdifferenz von null belegt, dass der Umlageprozess weder stillschweigend Ausgaben fallengelassen noch erzeugt hat.

**7. Formel**

<details>
<summary>Abstimmung von Quelle zu Umlage</summary>

```excel
=IF(
    ABS(
        CPL_Source_Total_Expense
        - CPL_Allocated_Total_Expense
    ) <= cfg_Tolerance,
    "✅ Reconciled",
    "❌ Difference Requires Review"
)
```

Dieselbe Kontrolle kann erweitert werden, um den Gesamtbetrag der Umlage-Engine mit der aggregierten Ausgabe auf Einrichtungsebene zu vergleichen.

</details>
### Beispielszenario

Betrachten Sie ein Unternehmen für Betreutes Wohnen mit drei aktiven Einrichtungen:

| Einrichtung |      Umsatz | Direkte Ausgabe |
| --------- | -----------: | -------------: |
| Einrichtung A    |     180.000 $ |       126.000 $ |
| Einrichtung B    |     150.000 $ |       112.500 $ |
| Einrichtung C    |     120.000 $ |        96.000 $ |
| **Gesamt** | **450.000 $** |   **334.500 $** |

Vor den Gemeinkosten beträgt der kombinierte Deckungsbeitrag:

```text
$450,000 − $334,500 = $115,500
```

Das Unternehmen hat im Monat zudem zwei gemeinsame Ausgaben:

| Gemeinsame Ausgabe     |  Betrag | Umlage      |
| ------------------ | ------: | --------------- |
| Fahrzeugausgaben   |  3.000 $ | 40 % / 35 % / 25 % |
| Unternehmens-Overhead | 24.000 $ | 25 % / 35 % / 40 % |

Die resultierende Gemeinkostenbelastung ist:

| Einrichtung |    Fahrzeug |   Unternehmen | Gemeinkosten gesamt |
| --------- | ---------: | ----------: | ----------------: |
| Einrichtung A    |     1.200 $ |      6.000 $ |            7.200 $ |
| Einrichtung B    |     1.050 $ |      8.400 $ |            9.450 $ |
| Einrichtung C    |       750 $ |      9.600 $ |           10.350 $ |
| **Gesamt** | **3.000 $** | **24.000 $** |       **27.000 $** |

Die Rentabilität der Einrichtungen wird dann:

| Einrichtung   | Deckungsbeitrag | Gemeinkosten | Nettogewinn | Nettomarge |
| ------ | -----------: | ----------: | ---------: | ---------: |
| Einrichtung A |      54.000 $ |      7.200 $ |    46.800 $ |      26,0 % |
| Einrichtung B |      37.500 $ |      9.450 $ |    28.050 $ |      18,7 % |
| Einrichtung C |      24.000 $ |     10.350 $ |    13.650 $ |      11,4 % |

Die wichtige Management-Erkenntnis ist nicht einfach, dass Einrichtung C die niedrigste Marge hat.

Das Modell macht die Schlussfolgerung präziser:

* Einrichtung C hat bereits vor den Gemeinkosten den schwächsten Deckungsbeitrag.
* Sie fängt zudem den größten Unternehmens-Overhead-Prozentsatz auf.
* Ihre finale Marge fällt daher auf 11,4 %.
* Einrichtung A bleibt komfortabel über der konfigurierten Zielmarge.
* Einrichtung C wird zum klarsten Kandidaten für eine operative Überprüfung.

Auf Unternehmensebene:

```text
Revenue
= $450,000

Direct Expense
= $334,500

Shared Expense
= $27,000

Consolidated Net Income
= $88,500
```

Die 27.000 $ an Gemeinkosten müssen exakt auf die Fahrzeugtransaktion von 3.000 $ plus die Unternehmens-Overhead-Transaktion von 24.000 $ abstimmen.

Die Umlage ändert die Gesamtausgaben des Unternehmens nicht. Sie ändert **wo das Management die Ausgabe sieht**.


### Formelreferenz

Die Arbeitsmappe stützt sich auf eine kleine Menge moderner Excel-Funktionen. Das Designziel ist nicht Formelkomplexität um ihrer selbst willen. Jede Formel existiert, um eine Geschäftsregel durchzusetzen: **korrekt klassifizieren, vollständig umlegen, konsistent aggregieren und das Ergebnis abstimmen**.

<details>
<summary>00_Setup — Kontrollen der Umlageregeln</summary>

#### Regelgesamtbetrag nach Umlage-ID

```excel
=SUMIFS(
    tbl_Allocation_Rules[Rule_Percent],
    tbl_Allocation_Rules[Rule_ID],
    [@Rule_ID]
)
```

**Zweck:** Berechnet den vollständigen Umlageprozentsatz für jede `Rule_ID`.

Da eine Regel mehrere Zieleinrichtungen enthalten kann, aggregiert `SUMIFS` jede Zeile, die zur selben Regel gehört.

Eine gültige Regel muss auf 100 % summieren, vorbehaltlich `cfg_Tolerance`.

#### Regelstatus

```excel
=LET(
    total_pct, [@[Rule_Total_Check]],
    tolerance, cfg_Tolerance,
    diff, total_pct - 1,
    IF(
        ABS(diff) <= tolerance,
        "✅ OK",
        IF(
            diff < 0,
            "⚠️ 欠分配",
            "❌ 超额分配"
        )
    )
)
```

**Zweck:** Verhindert, dass eine unvollständige oder übermäßige Umlageregel als gültig behandelt wird.

Die Toleranz ist zentralisiert, damit dieselbe numerische Kontrolle in der gesamten Arbeitsmappe wiederverwendet werden kann.

#### Eindeutige Regel-Prüfliste

```excel
=LET(
    u_rules, UNIQUE(tbl_Allocation_Rules[Rule_ID]),
    rule_desc,
        XLOOKUP(
            u_rules,
            tbl_Allocation_Rules[Rule_ID],
            tbl_Allocation_Rules[Rule_Desc]
        ),
    rule_sum,
        MAP(
            u_rules,
            LAMBDA(
                r,
                SUMIFS(
                    tbl_Allocation_Rules[Rule_Percent],
                    tbl_Allocation_Rules[Rule_ID],
                    r
                )
            )
        ),
    rule_chk,
        IF(
            ABS(rule_sum - 1) <= cfg_Tolerance,
            "✅ 闭环",
            "❌ 异常需核查"
        ),
    HSTACK(
        u_rules,
        rule_desc,
        rule_sum,
        rule_chk
    )
)
```

**Zweck:** Erzeugt je Umlageregel eine Prüfzeile auf Managementebene, statt Anwender zu zwingen, einzelne Regeldatensätze manuell zu inspizieren.

`UNIQUE` identifiziert die Regeln, `MAP` berechnet den Umlagegesamtbetrag jeder Regel, und `HSTACK` baut die Prüfansicht zusammen.

</details>

```excel
=LET(

        AND(
            cost_type = "Shared",
            ISBLANK(rule_id)

        AND(

            NOT(ISBLANK(unit_id))

        AND(
```

* ungültigen Beträgen;
* ungültigen Buchungsperioden;
* unbekannten Konten;
* fehlenden Direktzuordnungen zu Einrichtungen;
* unpassenden Umlageregeln;
* unvollständigen Umlageregeln;
* widersprüchlichen Einrichtungs-/Regelzuordnungen;
* Umsatz, der fälschlich als gemeinsame Ausgabe klassifiziert ist.

Dies geschieht bewusst vor der Rentabilitätsaggregation.

<details>
<summary>02_Allocation_Engine — Direkte und gemeinsame Umlage</summary>

#### Behandlung direkter Transaktionen

Eine gültige direkte Transaktion ist im Grunde eine 1:1-Zuordnung:

```text
Source Transaction
       ↓
One Unit
       ↓
100% Applied Rate
       ↓
Original Amount
```

Der angewandte Satz ist daher:

```excel
=1
```

Der umgelegte Betrag bleibt der ursprüngliche Transaktionsbetrag.

#### Behandlung gemeinsamer Transaktionen

Gemeinsame Transaktionen erfordern eine 1:n-Transformation.

Zum Beispiel:

```text
TX-2026-0001
$3,000
VEH-001
     │
     ├── UNIT-A   40%   $1,200
     ├── UNIT-B   35%   $1,050
     └── UNIT-C   25%   $750
```

Die Arbeitsmappe verwendet `FILTER`, `REDUCE`, `LAMBDA`, `HSTACK`, `VSTACK` und `EXPAND`, um diese erweiterte analytische Population zu konstruieren.

Die Kernbetragsberechnung ist:

```excel
=ROUND(
    row_amt * target_pcts,
    2
)
```

**Zweck:** Wandelt ein einzelnes gemeinsames wirtschaftliches Ereignis in mehrere analytische Zeilen auf Einrichtungsebene um, ohne die ursprüngliche Quelltransaktion zu verändern.

#### Vollständiges Muster der Umlage-Engine

```excel
=LET(
    valid_tx,
        FILTER(
            tbl_Transactions,
            tbl_Transactions[Tx_Calc_Audit_Alert] = "✅ 校验通过"
        ),

    is_direct,
        CHOOSECOLS(valid_tx, 5) = "Direct",

    is_shared,
        CHOOSECOLS(valid_tx, 5) = "Shared",

    /* Direct rows are passed through at 100%. */

    /* Shared rows are matched against
       tbl_Allocation_Rules and expanded
       into target-unit rows. */

    /* Final output is assembled with VSTACK
       and receives a sequential allocation-row ID. */
)
```

Der wichtige architektonische Punkt ist, dass die Engine den Anwender **nicht** auffordert, die Umlage manuell zu berechnen.

Sie empfängt:

```text
Transaction + Rule ID
```

und erzeugt:

```text
Transaction + Target Unit + Applied Rate + Allocated Amount
```

Die Engine wird damit zur kontrollierten Grenze zwischen Quellbuchhaltungsdaten und Management-Reporting.

</details>

<summary>04_Consolidated_PL — Dreifache Abstimmung</summary>

Die Konsolidierungsschicht trennt Reporting bewusst von Abstimmung.

Drei Populationen werden verglichen:

```text
Source Transactions
        ≡
Allocation Engine
        ≡
Unit P&L Roll-up
```

#### Gesamtbetrag der Quellausgaben

```excel
=LET(
    target_month, sel_Consol_Month,
    valid_tx,
        FILTER(
            tbl_Transactions,
            tbl_Transactions[Tx_Calc_Audit_Alert] = "✅ 校验通过"
        ),
    tx_cat, CHOOSECOLS(valid_tx, 11),
    tx_month, CHOOSECOLS(valid_tx, 9),
    tx_amt, CHOOSECOLS(valid_tx, 6),

    IF(
        target_month = "All-Year",
        SUMIFS(tx_amt, tx_cat, "<>Revenue"),
        SUMIFS(
            tx_amt,
            tx_cat, "<>Revenue",
            tx_month, target_month
        )
    )
)
```

#### Gesamtbetrag der Ausgaben der Umlage-Engine

```excel
=LET(
    target_month, sel_Consol_Month,
    eng_months,
        INDEX('02_Allocation_Engine'!A3#, , 3),
    eng_accts,
        INDEX('02_Allocation_Engine'!A3#, , 5),
    eng_amts,
        INDEX('02_Allocation_Engine'!A3#, , 9),

    is_exp,
        LEFT(eng_accts, 3) = "EXP",

    IF(
        target_month = "All-Year",
        SUM(FILTER(eng_amts, is_exp, 0)),
        SUM(
            FILTER(
                eng_amts,
                is_exp * (eng_months = target_month),
                0
            )
        )
    )
)
```

#### Abstimmungsdifferenz

```excel
=ABS(I5 - I6) + ABS(I6 - I7)
```

Die Berechnung erfasst beide Übergänge:

```text
Source → Engine
Engine → Unit Roll-up
```

#### Finales Prüfurteil

```excel
=LET(
    diff, I9,
    tolerance, cfg_Tolerance,
    IF(
        diff <= tolerance,
        "🟢 100% 勾稽平衡 (零双计 / 零遗漏)",
        "🔴 勾稽异常: 需核查"
    )
)
```

Die Abstimmungskontrolle ist bewusst unabhängig vom Dashboard.

Ein visuell plausibles Dashboard wird nicht als Beleg dafür behandelt, dass die zugrunde liegenden Daten vollständig sind.

</details>

### Validierungsregeln

Das Validierungsframework operiert auf mehreren Ebenen. Die Eingabevalidierung schützt die Quellpopulation; die Regelvalidierung schützt die Umlagelogik; die Abstimmung schützt die finale Berichtspopulation.

| Feld / Kontrolle          | Regel                                                             | Fehlerverhalten                                             |
| ------------------------ | ---------------------------------------------------------------- | ---------------------------------------------------------- |
| `Tx_ID`                  | Muss eine eindeutige Quelltransaktion identifizieren                        | Doppelte Datensätze sollten vor dem Reporting untersucht werden  |
| `Tx_Date`                | Muss ein gültiges Transaktionsdatum enthalten                            | Ungültiges Datum verhindert eine verlässliche monatliche Klassifizierung      |
| Analysejahr            | Transaktionsjahr sollte `cfg_AnalysisYear` entsprechen                 | `⚠️` Warnung bei Jahresüberschreitung                                |
| `Tx_Amount`              | Muss größer als null sein                                        | `❌` Transaktion wird aus der gültigen Berechnungspopulation ausgeschlossen |
| `Tx_Account_Code`        | Muss im Kontenstamm existieren                                     | `❌` unbekanntes Konto                                        |
| `Tx_Cost_Type`           | Muss `Direct` oder `Shared` sein                                     | Ungültige Klassifizierung muss korrigiert werden                   |
| Direkte Transaktion       | Muss eine `Tx_Direct_Unit_ID` angeben                             | `❌` fehlende Einrichtung                                           |
| Direkte Transaktion       | Darf keine Umlageregel angeben                              | `❌` widersprüchliche Zuordnung                                 |
| Gemeinsame Transaktion       | Muss eine gültige `Tx_Allocation_Rule_ID` angeben                   | `❌` fehlende Regel                                           |
| Gemeinsame Transaktion       | Darf keine direkte Einrichtung angeben                                   | `❌` widersprüchliche Zuordnung                                 |
| Gemeinsame Umlageregel   | Gesamtprozentsatz muss innerhalb der Toleranz 100 % betragen                | `⚠️` Unterumlage oder `❌` Überumlage               |
| Umsatzklassifizierung   | Umsatz darf nicht als gemeinsame Ausgabe behandelt werden                    | `❌` Klassifizierungskonflikt                                |
| Aktive Einrichtung              | Einrichtung muss im Einrichtungsstamm existieren                               | Transaktion sollte nicht zu einer undefinierten Berichtseinrichtung fließen |
| Umlageergebnis       | Umgelegter Betrag muss sich aus Quellbetrag und angewandtem Satz ableiten | Jede unerklärliche Differenz erfordert Prüfung                 |
| Quelle vs. Engine         | Quellausgabe muss auf Engine-Ausgabe abstimmen                  | Abstimmungsfehler                                     |
| Engine vs. Einrichtungs-GuV       | Engine-Ausgabe muss auf Einrichtungszusammenführung abstimmen                    | Abstimmungsfehler                                     |
| Dreifache Abstimmung | Alle Berichtspopulationen müssen innerhalb `cfg_Tolerance` bleiben     | Konsolidierter Prüfstatus wird rot                                  |
| Überlaufbereich für dynamische Arrays | Muss frei von Hindernissen bleiben                                         | Excel zeigt `#SPILL!` an                                   |
| Formelzellen          | Dürfen nicht manuell überschrieben werden                                 | Berechnungskette wird ungültig                                  |
| Berichtsmonat          | Muss `All-Year` oder eine gültige verfügbare Periode sein                   | Ungültige Auswahl sollte nicht für das Reporting verwendet werden         |

### Betriebsgrenzen und Wartung

Die Arbeitsmappe ist um modernes Excel herum konzipiert, nicht um Abwärtskompatibilität mit alten Tabellenkalkulationen.

**Unterstützte Umgebung**

* Microsoft 365 unter Windows oder Mac.
* Office 2021 oder neuer.
* Dynamische-Array-Funktionen einschließlich `LET`, `FILTER`, `UNIQUE`, `SORT`, `HSTACK`, `VSTACK`, `MAP`, `LAMBDA`, `REDUCE` und `EXPAND`.

Ältere Excel-Versionen können `_xlfn`-Fehler zurückgeben oder die Dynamische-Array-Berechnungskette nicht auswerten.

**Empfohlenes Datenvolumen**

Das Modell ist für etwa **100.000 Quelltransaktionszeilen** als praktischen Betriebsbereich ausgelegt.

Für Organisationen mit wesentlich größeren jährlichen Transaktionspopulationen empfiehlt die Quellarchitektur die Trennung in Jahresarbeitsmappen, statt eine einzelne Arbeitsmappe zu einer unternehmensweiten Datenbank zu machen.

**Mehrbenutzerbetrieb**

Die Arbeitsmappe kann über OneDrive oder SharePoint für kollaborativen Zugriff gespeichert werden. Regelwartung und Monatsabschluss-Abstimmung sind jedoch kontrollsensitive Tätigkeiten.

Die bevorzugte Betriebspraxis ist:

```text
Routine transaction entry
        ↓
Collaborative access where appropriate
        ↓
Controlled rule maintenance
        ↓
Dedicated month-end review
        ↓
Reconciliation sign-off
```

Die Umlageregeltabelle sollte während eines Abschlussprozesses nicht von mehreren Benutzern gleichzeitig bearbeitet werden.

### Monatlicher Standardbetriebsablauf

Der vorgesehene wiederkehrende Workflow ist:

```text
1. Maintain allocation rules
          ↓
2. Enter / import transactions
          ↓
3. Review transaction validation
          ↓
4. Confirm consolidated reconciliation
          ↓
5. Review unit profitability
          ↓
6. Present dashboard results
```

#### Schritt 1 — Umlageregeln prüfen

Bestätigen Sie:

* Analysejahr;
* aktive Einrichtungen;
* Kontenstamm;
* Gemeinkosten-Umlageprozentsätze.

Jede aktive Umlageregel sollte einen gültigen 100-%-Status ausweisen.

#### Schritt 2 — Transaktionen laden

Direkte Transaktionen benennen ihre Einrichtung.

Gemeinsame Transaktionen benennen ihre Umlageregel.

Eine gemeinsame Ausgabe bleibt eine einzige Quelltransaktion:

```text
Correct:
$10,000 Corporate Overhead
Rule = CORP-001

Incorrect:
$2,500 Unit A
$2,500 Unit B
$2,500 Unit C
$2,500 Unit D
```

Der zweite Ansatz zerstört die Unterscheidung zwischen dem Quellereignis und seiner Management-Umlage.

#### Schritt 3 — Transaktionsvalidierung ausführen

Filtern Sie die Prüf-Alarm-Spalte und beheben Sie alle Fehler, bevor Sie sich auf die nachgelagerte Rentabilität stützen.

Eine Transaktion, die die Validierung nicht besteht, sollte nicht allein deshalb als gleichwertig zu einer gültigen Transaktion behandelt werden, weil ihr Betrag plausibel erscheint.

#### Schritt 4 — Abstimmung bestätigen

Das konsolidierte Prüfcenter sollte vor dem Management-Reporting den grünen abgeglichenen Zustand anzeigen.

Falls nicht, sollte das Dashboard nicht als final behandelt werden.

#### Schritt 5 — Einrichtungsrentabilität prüfen

Wechseln Sie zwischen `All-Year` und einzelnen Monaten.

Prüfen Sie:

* Umsatz;
* direkte Kosten;
* Deckungsbeitrag;
* umgelegte Gemeinkosten;
* Gesamtkosten;
* Nettogewinn;
* Gewinnmarge;
* Zustandsklassifizierung.

Die Schlüsselfrage ist, ob schwache Rentabilität aus lokaler Betriebswirtschaftlichkeit oder Gemeinkostenaufnahme stammt.

#### Schritt 6 — Managementergebnisse präsentieren

Das Dashboard kondensiert die validierte Population auf Einrichtungsebene zu:

* Unternehmensumsatz;
* Unternehmensausgaben;
* Unternehmens-Nettogewinn;
* Unternehmensmarge;
* leistungsstärkste Einrichtung;
* leistungsschwächste Einrichtung;
* Gemeinkostenbelastung.

Das Dashboard ist damit die finale Präsentationsschicht, nicht die Quelle der Wahrheit.

### Fehlerbehebung

#### `#SPILL!` erscheint in der Arbeitsmappe

Dynamische-Array-Formeln erfordern, dass ihr vorgesehener Überlaufbereich frei bleibt.

Typische Ursachen sind:

* manuell eingegebene Werte;
* versteckte Leerzeichen;
* kopierte Formatierung kombiniert mit Inhalt;
* verbundene Zellen;
* eine weitere Formel, die den Überlaufbereich belegt.

Wählen Sie die Quellformelzelle aus und prüfen Sie die hervorgehobene Überlaufgrenze. Entfernen Sie den hindernden Inhalt aus dem Überlaufbereich, statt die Formel manuell nach unten zu kopieren.

#### Eine neue Einrichtung erscheint nicht in der GuV

Prüfen Sie:

1. Die Einrichtung existiert in `tbl_Dim_Unit`.
2. `Dim_Unit_Status` ist `Active`.
3. Die Einrichtungs-ID ist eindeutig.
4. Kein Inhalt blockiert die Dynamische-Array-Ausgabe.

Die Berichtsmatrix wird von aktiven Einrichtungsstammdaten getrieben statt von einer festen Spaltenliste.

#### Eine gemeinsame Ausgabe wird nicht umgelegt

Prüfen Sie:

1. `Tx_Cost_Type = Shared`.
2. `Tx_Allocation_Rule_ID` ist gefüllt.
3. Die Regel existiert.
4. Der Regelstatus ist `OK`.
5. Die Zieleinrichtungen existieren.
6. Die Prozentwerte summieren sich innerhalb der konfigurierten Toleranz auf 100 %.

#### Die konsolidierte Abstimmung ist rot

Passen Sie das Abstimmungsergebnis nicht manuell an.

Verfolgen Sie die Kette:

```text
Source Transaction
       ↓
Transaction Validation
       ↓
Allocation Rule
       ↓
Allocation Engine
       ↓
Unit P&L
       ↓
Consolidated Roll-up
```

Der Zweck der Abstimmungsschicht ist genau, zu identifizieren, wo die Kette aufgehört hat zu übereinstimmen.

</details>

## Die Geschäftslogik & Methodik

Das Modell verwendet ein einfaches Prinzip der Betriebsbuchführung: **die Quelltransaktion bleibt intakt, während die Reporting-Behandlung separat angewandt wird**. Dies macht die Gemeinkostenumlage sichtbar, ohne Umlage mit dem ursprünglichen wirtschaftlichen Ereignis zu verwechseln.

* **Kontrolle über Quelltransaktionen aus einer Hand** — Gemeinkosten werden einmal erfasst und dann nach einer expliziten Geschäftsregel verteilt. Das reduziert doppelte Erfassung und wahrt einen sauberen Quellpfad. Die Managemententscheidung wird: *welche Einrichtungen sollten diese Kosten auffangen, und auf welcher vereinbarten Basis?*

* **Regelbasierte Kostenumlage** — Jede gemeinsame Ausgabe verweist auf eine definierte Verteilungsregel. Da die Regel auf 100 % schließen muss, kann das Management eine echte Umlage von einer unvollständigen Schätzung unterscheiden. Die Entscheidung wird, ob die Umlagebasis kommerziell angemessen ist, statt ob die Tabellenkalkulation zufällig aufgegangen ist.

* **Deckungsbeitrags-Rentabilitätsanalyse** — Direkte Betriebswirtschaftlichkeit wird von Gemeinkostenaufnahme getrennt. Dies verhindert, dass eine Einrichtung mit starkem lokalem Betrieb allein auf einem vollständig belasteten Ergebnis beurteilt wird, ohne zu verstehen, was die Differenz treibt.

* **Schwellenbasierte Betriebsalarme** — Rentabilität wird mit einem konfigurierbaren Managementziel verglichen. Dies verwandelt einen langen Finanzbericht in eine priorisierte Betriebsüberprüfung: welche Einrichtungen gute Leistung zeigen, welche Kostenkontrolle benötigen und welche sofortige Aufmerksamkeit erfordern.

* **Dreifache Abstimmung** — Quellausgaben, umgelegte Ausgaben und Ausgaben auf Einrichtungsebene werden vor dem Management-Reporting verglichen. Dies stellt sicher, dass der Umlageprozess den *Ort der Kosten* ändert, nicht die Gesamtkosten des Unternehmens.

Die Methodik handelt daher weniger davon, noch eine GuV zu produzieren, und mehr davon, die Kette von **wirtschaftlichem Ereignis → Umlage → Einheitsökonomie → konsolidiertem Ergebnis** prüfbar und verständlich zu machen.
